# 全站公告与通知

本文档说明 Obsidian Arc 的常驻主页通知与广播公告的配置方式、已读跟踪机制与排查路径。

---

## 1. 常驻主页通知 (Home Notice)

常驻通知是站点的全局配置，悬挂在主对话区域最上方。

### 配置说明
管理员可在「系统设置」中配置：
- **通知内容 (`home.notice`)**：支持 Markdown 格式；
- **允许关闭 (`home.notice_dismissible`)**：
  - `true`：用户点击关闭按钮后，当前设备不再展示该通知；
  - `false`：通知始终常驻悬浮，不可被关闭，适用于重大维护告示。

---

## 2. 广播公告系统 (Announcements)

广播公告用于发布具备生命周期、需要弹窗提醒或记录已读状态的正式通知。

### 做了什么
1. **富文本支持**：包含标题与 Markdown 正文，支持列表与链接；
2. **展示机制**：支持模态弹窗强提醒（登录后弹出）以及通知铃铛红点提示；
3. **用户已读状态持久化**：系统在 `announcement_reads` 表中记录用户 ID 与公告 ID 的关联，用户确认知晓后写入已读记录，后续登录不再弹出。

### 为什么这么做
确保重要通知能够切实传达给每位活跃用户，同时避免每次刷新页面均重复弹出打扰正常交互。

### 代价是什么
每个用户对每条公告的已读状态均产生一条数据库行记录，用户规模较大时会增加关系表的行数。

---

## 运维约束与排查路径

### 失效场景
1. **公告在未登录访客端重复弹出**：访客无用户 ID，无法在数据库中记录已读状态，因此在每次以访客身份进入时均可能重复显示弹窗；
2. **Markdown 语法解析异常**：若公告中包含未闭合的代码块或特殊标签，可能导致通知区域排版异常。

### 不明显的约束与前提
1. **常驻通知与弹窗公告生命周期分离**：常驻通知 `home.notice` 属于全站动态配置，修改即时刷新且无已读状态控制；弹窗公告属于独立实体，已读记录持久化于 `announcement_reads` 表中且按用户绑定；
2. **客户端时钟依赖**：公告的生效与过期基于时间戳对比，若宿主机或客户端时钟发生严重漂移，可能导致公告提前过期或未按时展示；
3. **已读状态不可逆**：用户点击确认已读后，已读记录即时写入数据库，系统未提供面向普通用户的“标记为未读”入口，管理员重发通知需创建新公告。

### 排查步骤
1. **核实公告是否上线**：在管理后台「全站公告」列表中检查公告的状态是否处于启用状态，核对生效时间范围；
2. **已读记录排查**：若特定用户未收到弹窗提示，查询数据库中该用户是否已存在该公告的已读记录。
