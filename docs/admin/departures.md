# 退群处理与邀请回收

成员退出了 QQ 群之后，站点这边要做两件事：把他的账号处理掉（封禁或删除），并且把他当初通过邀请进来时让邀请人拿到的重置卡收回来。这两件事由一个原子操作完成，既可以在后台人工触发，也可以由你的 QQ 机器人通过 Webhook 自动触发。机器人对接协议见[下文第五节](#五、机器人接入协议)，那是给机器人开发者的完整接口说明。

## 一、功能概述

本站看不到 QQ 群本身，所以「有人退群」永远不会被自动感知——它总是由两个入口之一带进来：后台的人工操作，或机器人的上报。两个入口跑的是同一个核心逻辑，一次事务里完成全部动作：

1. 锁定被处理账号，读取它的邀请记录（它让邀请人得到了几张卡）；
2. 从邀请人手里收回相应数量的**未使用、未过期**的重置卡（快过期的先收）；
3. 写入一条退群记录（墓碑行，保留账号被删后的历史）；
4. 记入安全日志；
5. 提交之后给邀请人发一条站内通知。

### 封禁与删除

两个档位是两种不同的决定，不是同一件事的两个力度：

| | 封禁 (disable) | 删除 (delete) |
| --- | --- | --- |
| 账号数据 | 全部保留 | 会话、对话、附件、API 密钥、卡、邀请记录等全部级联删除 |
| 状态 | `disabled`，登录与会话立即失效 | 账号行删除，一切登录立即失效 |
| QQ 号 | 仍被占用，同 QQ 无法重新注册 | 释放，同 QQ 可以重新注册 |
| 可否恢复 | 管理员可以随时恢复 | 不可恢复 |
| 邀请记录 | `invite_uses` 保留 | 随级联删除，展示由退群记录补回 |

默认建议是封禁：一次误报的代价只是管理员手动恢复一下，而删除档下同 QQ 立刻可以重新注册，惩罚反而可能被绕过。

### 收卡规则

收卡按账本精确计算，而不是一律收一张：

- 收回数量 = 这个被邀请人当初让邀请人得到的卡数（邀请结算账本 `invite_uses` 里记录的数字，默认配置下每邀请满 N 人发 M 张，只有落在里程碑上的那次邀请才发过卡）。
- 奖励**从未结算**的（还没通过邮箱验证、被 same_ip 跳过、未达里程碑等），按 0 张算——当年没发过，现在也不收。
- 邀请人已经把卡用掉的部分**不会从别处补收**：应收回和实际收回是两个数字，接口和通知都如实分开报告。
- **每次邀请只收一次**。封禁退群后又恢复、之后再次退群的，第二次处理会记录在案但不再收卡；机器人重复上报同一个人也不会重复扣卡。

## 二、后台操作

「用户」页面打开某个账户的面板，底部「退群处理」区有两个按钮：**封禁账号并收回卡片**和**删除账号并收回卡片**。删除档需要二次确认；操作完成后会显示「应收回 X 张，实际收回 Y 张」。

「邀请码」页面有「退群记录」卡片：所有已处理的退群，按时间倒序，每一行是被处理人（用户名 + QQ）、邀请人、处理方式、应收回/实收回卡数、处理方（后台操作或 QQ 机器人）和时间。删除档下被处理人的账号已经不存在，这一行来自退群记录本身。

邀请人会在自己的「设置 → 邀请」里看到变化：退群的被邀请人标记为「已退群」（删除档为「已退群 · 账号已删除」），并注明收回了多少张卡。同时收到一条站内通知。

SSH / Web 终端里对应的命令：

```
user depart <id|username> [--mode=disable|delete] [--note TEXT] --yes
invite departures
```

## 三、配置

两个设置键都在后台「安全」页面的注册区：

| 设置键 | 默认值 | 用途 |
| --- | --- | --- |
| `bot.webhook_token` | 空 | 机器人 Webhook 的 Bearer 令牌。**留空 = 接口整体关闭**。写后不可再查看，输入框留空保存表示保留原令牌 |
| `bot.departure_mode` | `disable` | 机器人上报的事件未指定方式时使用的默认档位 |

没有配置令牌的实例，机器人接口对一切请求都返回 401，和功能未上线时的表现一致。

## 四、管理接口

两个接口都挂在后台鉴权之后（管理员会话 + 权限 + 两步验证策略），与浏览器后台调用的是同一套。

### 处理退群

```
POST /api/admin/users/{id}/departure
```

请求体：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `mode` | string | 是 | `disable` 或 `delete` |
| `note` | string | 否 | 备注，记入退群记录与安全日志 |

响应 `200`，`departure` 字段为处理结果（字段见[机器人协议](#五、机器人接入协议)的 `result` 表）。

| 场景 | 状态码 | 错误码 |
| --- | --- | --- |
| 方式不是 disable/delete | 400 | `departure_mode` |
| 处理自己的账号 | 400 | `bad_request` |
| 该账号已经处理过退群（重复点击、机器人已处理过） | 409 | `already_departed` |
| 目标是管理员账号（管理员的去留只能由管理员判断，见安全模型一节） | 409 | `departure_refused` |
| 目标是最后一个活跃超级管理员 | 409 | `last_admin` |
| 账号不存在 | 404 | `not_found` |

### 退群记录列表

```
GET /api/admin/departures?limit=50&offset=0
```

响应 `200`：`{ "departures": [...], "total": 10 }`，按时间倒序分页。每一行：

| 字段 | 说明 |
| --- | --- |
| `id` | 记录 id |
| `user_id` / `username` / `qq` | 被处理人的快照（删除档下账号已不存在，快照是唯一出处） |
| `inviter_id` / `inviter_name` | 邀请人；邀请人后来也被删除时 `inviter_name` 为空字符串 |
| `mode` | `disable` 或 `delete` |
| `reward_cards_due` / `cards_revoked` | 这次事件应收回 / 实际收回的卡数 |
| `source` | `admin` 或 `bot` |
| `actor_id` | 处理的管理员 id，机器人为空 |
| `note` / `created_at` | 备注与时间（epoch 毫秒） |

## 五、机器人接入协议

这一节是机器人开发者的完整接口说明。协议是**单向**的：机器人向站点上报退群事件，站点返回处理结果。

### 端点与鉴权

```
POST /api/bot/departure
Authorization: Bearer <token>
```

- 令牌就是设置键 `bot.webhook_token` 的值，在后台「安全」页配置；没有配置令牌时接口整体关闭。
- 服务端用常量时间比较令牌。令牌缺失、令牌错误、接口未启用三种情况返回**完全相同**的 401，不泄露任何区别。
- 不需要 Cookie、会话或 CSRF 令牌。机器人是普通 HTTP 客户端，**不要主动携带 `Origin` 头**（带了一个不属于本站的 Origin 会被同源校验拒绝；不携带则正常通过）。

### 请求体

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `qq` | string | 是 | 退群成员的 QQ 号，5-15 位数字（`^[1-9][0-9]{4,14}$`） |
| `mode` | string | 否 | `disable` 或 `delete`；缺省时用实例默认档 `bot.departure_mode` |

### 响应：状态词

除了传输层错误，**所有正常业务结果都是 HTTP 200 + 状态词**——上报退群是机器人的本职，「这个 QQ 不存在」不是失败，机器人可以直接把状态词翻译成群里的播报文案：

| status | 含义 | `result` |
| --- | --- | --- |
| `departed` | 处理成功 | 完整结果，见下表 |
| `already_departed` | 该 QQ 已经处理过（幂等），本次没有重复收卡 | 删除档重复上报时回传当初的处理结果；封禁档重复上报时为空对象 |
| `unknown` | QQ 号没有对应的账号（从未注册，或已被删除且无退群记录） | 空 |
| `refused` | 目标是管理员账号，机器人无权处理 | 空 |

`result` 字段（`departed` 时总有值）：

| 字段 | 说明 |
| --- | --- |
| `user_id` | 账号 id（删除档下该账号现已不存在，此 id 仅作参考） |
| `username` | 账号用户名 |
| `qq` | 处理的 QQ 号 |
| `inviter_id` | 邀请人账号 id；不是通过邀请注册的为空字符串 |
| `mode` | 本次实际使用的档位 `disable` 或 `delete` |
| `cards_due` | 应收回卡数：这次邀请当初发出去的重置卡数量 |
| `cards_revoked` | 实际收回卡数：邀请人手里还没用掉的部分 |

`cards_due` 和 `cards_revoked` 可能不相等——邀请人已经用掉的卡不会从别处补收，差值就是已被花掉的。`cards_due = 0` 表示这次邀请从未发过奖励（被 same_ip 跳过、未达里程碑、当时奖励关闭等）。

### 错误响应

| HTTP | 错误码 | 场景 |
| --- | --- | --- |
| 401 | `bot_unauthorized` | 未带令牌、令牌错误，或接口未启用 |
| 400 | `bot_bad_qq` | `qq` 缺失或格式非法 |
| 400 | `bot_bad_mode` | `mode` 不是 disable/delete |
| 429 | `rate_limited` | 触发限流 |

错误响应体统一为 `{"error": {"code": "...", "message": "..."}}`。

### 限流

按来源 IP 的令牌桶：**突发 10 次**（机器人批量补报积压事件不会被掐断），持续速率约每 5 秒 1 次。限流只对**持有有效令牌**的请求计数——没有令牌的请求在常量时间比较处就被拒绝，不会消耗限流额度，也不会触碰数据库。收到 429 时等待几秒重试即可。

### 幂等与重试建议

| 情况 | 建议 |
| --- | --- |
| 网络失败 / 超时 | **重试安全**。同一个 QQ 重复上报只会得到 `already_departed`，绝不重复收卡 |
| 429 | 退避后重试（等待响应建议的几秒） |
| `unknown` | 不要重试。要么此人从未注册，要么已被彻底删除且无退群记录，重试结果不变 |
| `refused` | 不要重试。管理员账号只能由管理员在后台处理，可在群里提示「该账号需管理员处理」 |
| `already_departed` | 无需任何处理，说明之前已经上报成功 |

### 完整示例

处理成功（默认档位，QQ `123456789` 退出群聊）：

```http
POST /api/bot/departure HTTP/1.1
Host: example.com
Authorization: Bearer a-webhook-token-a-bot-keeps
Content-Type: application/json

{"qq": "123456789"}
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "status": "departed",
  "result": {
    "user_id": "01JXXXXXXXXXXXXXXXXXXXXXXX",
    "username": "someone",
    "qq": "123456789",
    "inviter_id": "01JYYYYYYYYYYYYYYYYYYYYYY",
    "mode": "disable",
    "cards_due": 1,
    "cards_revoked": 1
  }
}
```

指定删除档：请求体改为 `{"qq": "123456789", "mode": "delete"}`，响应里 `mode` 回显 `"delete"`。

QQ 不存在：

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"status": "unknown", "result": {}}
```

重复上报（幂等）：再次发送同一请求，得到 `{"status": "already_departed", "result": {…}}`。

令牌错误：

```http
HTTP/1.1 401 Unauthorized
Content-Type: application/json

{"error": {"code": "bot_unauthorized", "message": "This endpoint needs a valid bearer token."}}
```

### 机器人侧处理流程

推荐的事件处理顺序：

```
收到退群事件（群号, QQ 号）
  ↓
POST /api/bot/departure {"qq": QQ号}          // mode 留空，交给站点默认档
  ↓
按 status 分支：
  departed          → 播报「{username} 已退群」
  already_departed  → 静默或提示「已处理过」
  unknown           → 静默（此人未注册过站点）
  refused           → 播报「管理员账号请在站点后台处理」
  HTTP 429          → 退避重试
  其他网络错误       → 重试（幂等，安全）
```

播报文案建议带上 `cards_revoked`：`cards_revoked > 0` 时提示「已收回 N 张重置卡」，机器人不需要理解站内的卡体系，照抄数字即可。

## 六、安全模型与边界

- **机器人永远不能处理管理员账号**（`admin` / `super_admin`），无论令牌是否泄露。管理员的去留只能在后台由管理员决定，且受「最后一个超级管理员」守卫保护。后台人工处理管理员账号是允许的。
- **不能处理自己**：后台操作者无法对自身执行退群处理。
- 收卡的并发安全由数据库行锁保证：两个被邀请人同时退群时会串行处理，总收回量不会超过账本发出的总量。
- 令牌是唯一的门槛，请像对待密码一样对待它：只走 HTTPS、不要写进群公告或机器人日志。泄露后重新设置令牌即完成轮换（旧令牌立即失效）。
- 每一次处理都会写入安全日志（事件 `account_departure`，含处理方、档位、操作者与来源 IP），后台「安全事件」里可查。
