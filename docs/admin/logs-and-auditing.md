# 请求日志与排错

本文档说明 Obsidian Arc 的请求审计日志字段结构、错误下钻过滤逻辑、日志清理策略与排查路径。

---

## 日志记录结构

后端对每一次前端交互和 `/v1` 网关调用记录审计流水，写入 `request_logs` 表：

| 字段类别 | 记录项 | 说明 |
| :--- | :--- | :--- |
| **基础信息** | 全局请求 ID (ULID)、时间戳、客户端真实 IP、User-Agent | 标识请求发起来源与网络环境。 |
| **用户信息** | 用户 ID、用户名、所属用户组 | 明确请求归属与鉴权主体。 |
| **模型调度** | 服务商名称、目标模型名称、上游真实 Model ID | 记录路由目标与上游映射。 |
| **耗时与性能** | 总执行耗时 (ms)、首字延迟 TTFT (ms)、HTTP 状态码 | 衡量上游网络与生成速率。 |
| **用量统计** | 输入 Token、输出 Token、推理 Token、结算点数 | 记录实际 Token 消耗。 |
| **错误回包** | 原始错误文本、错误类型与错误码 | 记录上游服务商返回的原始 JSON 或网络报错。 |

---

## 模型错误下钻检索

### 做了什么
在管理后台「模型管理」列表中，每个模型条目均提供「查看历史报错」快捷按钮。点击后自动跳转至「请求日志」页面，并预设过滤条件：
- 过滤当前模型 ID；
- 状态码筛选为非 200。

### 为什么这么做
在多模型网关中，排查特定模型不可用时，在混合了全站所有正常请求的日志列表中手动查找效率较低。预填条件的下钻过滤可直接隔离目标模型的错误样本。

### 代价是什么
下钻操作基于 URL Query 传参并在页面初始化时发起单次数据库查询，若数据库索引不完善且历史数据量庞大，单次筛选查询可能耗时数秒。

---

## 过滤与检索维度

日志管理界面支持以下维度检索：
- **按 HTTP 状态码筛选**：隔离 `4xx` 客户端错误（如 401 密钥失效、429 配额不足）或 `5xx` 服务端异常（如 504 上游超时）；
- **按用户筛选**：审查特定高频调用用户的请求历史；
- **按耗时筛选**：定位执行耗时较长的慢请求；
- **按时间切片**：聚焦最近 1 小时、今日或自定义时间区间的日志。

---

## 日志保留与清理机制

### 做了什么
1. **手动清理**：管理员可在后台点击「清理日志」，删除指定天数以前的历史记录；
2. **定时修剪**：后台巡检任务按配置的保留周期定期修剪旧请求日志。

### 为什么这么做
高频并发下请求日志数据量增长迅速，若不设上限会持续占用数据库存储空间并降低日志查询的索引扫描效率。

### 代价是什么
旧日志清理后不可恢复，若发生跨越较长时间的安全事件排查，无法调阅已被清理时间段的详细调用流水。

---

## 运维约束与排查路径

### 失效场景
1. **日志未记录原始错误体**：若上游服务商直接中断 TCP 连接导致抛出 `unexpected EOF`，系统只能捕获到底层网络错误，无法获得上游业务错误码；
2. **日志单表过大影响检索性能**：在 SQLite 模式下单表记录数达到数百万行后，基于多条件的组合筛选会产生磁盘 I/O 峰值。

### 不明显的约束与前提
1. **日志写入时机滞后于推流完成**：请求日志在响应完全传输完毕或连接被客户端中断后执行写入，并使用 `context.WithoutCancel` 确保写入不丢失；因此无法在日志列表中实时查看当前正在进行中的活跃长连接；
2. **敏感 Header 与凭据已脱敏**：记录的原始请求信息中，`Authorization` 与 `x-api-key` 标头已被自动遮蔽，数据库日志不存储上游明文密钥；
3. **分表与修剪约束**：系统未引入按月自动分表机制，单张 `request_logs` 表依赖索引维护检索效率，必须配置定期清理周期（`health.retain_days`）控制表体积。

### 排查步骤
1. **定位 401 错误**：查看日志中的错误信息，若为 `invalid_api_key`，检查服务商的 API Key 是否填错或被服务商撤回；
2. **定位 429 错误**：核对是系统自身的配额已用尽，还是上游服务商返回了速率限制错误；
3. **定位 504 错误**：核对日志中的总耗时，若恰好等于反向代理或网关的超时阈值（如 90s），表明上游首字响应超时。
