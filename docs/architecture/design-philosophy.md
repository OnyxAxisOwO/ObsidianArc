# 架构设计与底层约束

本文档记录 Obsidian Arc 的系统架构设计、核心技术决策、设计取舍与运维排查路径。

## 单体架构

### 做了什么
系统采用单进程 Go 二进制设计，前端编译产物通过 Go 1.16+ 的 `embed.FS` 机制完整打包进可执行文件。后端内部划分为业务模块（位于 `internal/*`），每个模块按 `store.go`（数据读写）、`service.go`（业务逻辑）、`http.go`（路由与序列化）和 `types.go`（数据结构）组织。数据持久化依赖单一关系型数据库（SQLite 或 PostgreSQL），无独立缓存服务或消息代理。

### 为什么这么做
自托管部署要求环境准备和运维成本尽可能低。将前端资源与后端逻辑集成于单个二进制文件，配合嵌入式数据库，可以在无外部基础设施依赖的环境下直接运行，简化了私有化交付、单机运行与跨平台分发流程。

### 代价是什么
1. **模块无法独立伸缩**：所有业务逻辑运行在同一个操作系统进程内，无法针对高负载模块单独扩容。
2. **故障隔离粒度低**：任何模块发生未捕获的致命错误或内存泄漏，均会导致整个进程退出或崩溃。
3. **前端资源嵌入增加二进制体积**：前端产物打包至 Go 二进制中，使二进制体积增加约 1~2 MB，且修改前端静态文件必须重新编译或打包后端。

## 依赖管理

### 做了什么
后端仅使用 3 个直接外部依赖：
1. `modernc.org/sqlite`：纯 Go 实现的 SQLite 驱动，编译阶段不依赖 CGO 工具链；
2. `github.com/jackc/pgx/v5`：PostgreSQL 驱动与连接池实现；
3. `golang.org/x/crypto`：用于 Argon2id 密码哈希计算。

其余功能均基于 Go 标准库实现：HTTP 路由采用 Go 1.22 的 `net/http.ServeMux`（支持方法谓词与路径通配符），日志采用 `log/slog`，数据访问采用 `database/sql`。

### 为什么这么做
1. **跨平台交叉编译**：无 CGO 依赖使跨平台交叉编译（如从 Linux 编译 macOS/Windows 产物）无需配置交叉编译 C 编译器工具链。
2. **降低供应链攻击面**：依赖项越少，第三方依赖引入的安全漏洞或不兼容更新的风险越低。
3. **长期维护成本**：减少对外部大型 Web 框架或 ORM 库的依赖，避免框架重大版本升级造成的破坏性破坏。

### 代价是什么
1. **样板代码量增加**：没有 ORM 提供的自动化对象关系映射和动态查询构造器，所有 SQL 查询、参数绑定与字段扫描（`rows.Scan`）均需手工编写与维护。
2. **基础组件需自行封装**：请求上下文提取、统一错误响应、分页解析等功能需在 `internal/httpx` 中自行维护，缺少生态成熟中间件开箱即用的功能。

## 数据库抽象层

### 做了什么
系统通过 `database.Queryer` 接口封装查询执行。所有 SQL 查询统一使用 `?` 占位符编写，执行前由中间层根据当前数据库驱动进行动态重绑定：SQLite 保持 `?`，PostgreSQL 转换为 `$1, $2, ...`。
实体主键采用 26 位字符的 ULID，时间戳采用毫秒级整数（epoch milliseconds）。系统内置的数据库迁移脚本（位于 `internal/database/migrations/`）使用两套数据库通用的 SQL 子集编写。

### 为什么这么做
允许单个代码库同时支持轻量级单机场景（SQLite）与多节点部署场景（PostgreSQL），使用者切换数据库驱动无需修改业务代码。使用 ULID 避免了不同数据库自增序列（AUTOINCREMENT vs SERIAL/SEQUENCE）的语法分歧，同时在字符串排序上保留时间单调递增属性。

### 代价是什么
1. **不能利用数据库专有特性**：放弃了 PostgreSQL 的 JSONB 索引与特定操作符、生成列、特定存储过程等高级功能，限制了复杂查询的优化手段。
2. **占位符转换开销**：在 PostgreSQL 模式下，每次执行 SQL 都需要对 SQL 字符串进行扫描并替换占位符，存在纳秒级的内存分配与 CPU 开销。
3. **类型适配复杂**：二进制存储在 SQLite 中为 `BLOB`，在 PostgreSQL 中需统一转换为 `bytea`，迁移脚本中必须使用中间层预处理标记（如 `%BLOB%`）进行条件替换。

## 并发控制与行级锁

### 做了什么
涉及“先检查后写入”（Check-then-Write）的状态判断（包括配额预扣、管理员数量核验、卡密兑换），统一在数据库事务中通过显式更新行来获取行级锁：

```go
// 用户级并发判定：显式更新 updated_at 锁定用户记录行
tx.Exec(ctx, `UPDATE users SET updated_at = updated_at WHERE id = ?`, userID)

// 实例级并发判定：通过 settings 占位行锁定
tx.Exec(ctx,
    `INSERT INTO settings (key, value, updated_at) VALUES (?, ?, ?)
     ON CONFLICT (key) DO UPDATE SET updated_at = settings.updated_at`, ...)
```

### 为什么这么做
在多实例部署场景下，运行在各自进程内的 Go `sync.Mutex` 无法跨进程协调。若使用进程内互斥锁，请求被负载均衡分发至不同实例时，配额校验等逻辑会并发执行导致超额消耗。行级锁由底层数据库统一管理，保证跨进程互斥。

### 代价是什么
1. **锁争用延迟**：同单一用户发起高频并发请求时，后续请求必须在数据库连接池中排队等待前序事务提交，增加了平均响应时间。
2. **SQLite 并发写入瓶颈**：在 SQLite 模式下，写事务即使开启 WAL 模式也同一时间仅支持单个写入者，高并发写入时容易触发 `database is locked` 错误。

## 事务与外部调用的生命周期隔离

### 做了什么
系统规定数据库事务与上游模型 HTTP 调用完全解耦，分为两阶段执行：
1. **前置预扣阶段**：开启短事务，锁定用户行，根据模型最坏情况预估扣减配额，提交事务并释放数据库连接；
2. **流式传输阶段**：仅持有网络 Socket 与上游通信，不持有任何数据库连接或事务；
3. **后置结算阶段**：通信结束后，开启新的短事务，按实际消耗的 Token 结算并释放多扣额度。

### 为什么这么做
大语言模型的生成过程通常持续数秒到数分钟。如果在事务中保持数据库连接等待模型输出，少量并发请求就会在短时间内耗尽数据库连接池，导致整个系统全部接口（包括健康检查与静态资源请求）阻塞。

### 代价是什么
1. **存在中间不一致状态**：前置预扣后若宿主机突发掉电或进程被操作系统强制终止（SIGKILL），预扣的额度未能进入结算阶段，导致用户额度被短时间冻结，需等待定时巡检任务超时释放。
2. **业务逻辑拆分复杂**：必须编写预扣、正常结算、异常回退三套状态处理代码，增加了业务路径的测试复杂度。

## 请求生命周期与取消控制

### 做了什么
客户端主动断开连接（如点击停止或关闭网页标签页）会关闭 HTTP 连接并触发 `r.Context()` 取消，向模型服务商发起的外部 HTTP 请求随之被取消。随后的实际消耗结算与已接收内容保存，通过 `context.WithoutCancel(r.Context())` 继承链路值并在独立取消控制下执行。

### 为什么这么做
1. 立即中断上游调用可以停止上游计费，避免继续生成无用内容；
2. 中断前已接收的文本内容和已消耗的 Token 属于实际产生的开销，必须持久化并扣费，不能随请求上下文的取消而被丢弃。

### 代价是什么
脱钩后的持久化上下文不再受客户端请求超时控制。若数据库写入发生挂起，必须依靠数据库驱动的内部超时参数，否则协程可能出现滞留。

## 运维约束与排查路径

### 失效场景
1. **网络文件系统上的 SQLite**：若将 `./data` 挂载在 NFS、CIFS 或某些跨主机网络卷上，因文件锁语义不完整，会导致 SQLite 数据库损坏或频繁抛出 `disk I/O error`。生产多节点环境必须配置 PostgreSQL。
2. **SQLite 写入密集场景**：当大批量用户并发登录或高频兑换卡码时，SQLite 即使处于 WAL 模式也会因串行排队超时报错。
3. **上游服务商未实现即时断开计费**：部分第三方兼容中转服务在收到 TCP RST 或 HTTP 连接断开后，依然会在后台完整生成并按全量计费，本系统的上下文取消无法控制该类上游的计费逻辑。

### 不明显的约束与前提
1. **SQL 兼容约束**：所有新增数据表与字段必须编写在通用 SQL 语法子集内，严禁在 `internal/database/migrations/` 中添加特定数据库专有语法。CI 流水线中的 `internal/database/portability_test.go` 会在 SQLite 与 PostgreSQL 上双重运行所有迁移以进行静态与动态断言。
2. **连接池尺寸匹配**：环境变量 `OBSIDIAN_DB_MAX_CONNS` 默认针对 SQLite 为 4，针对 PostgreSQL 为 10。在高并发实例下需根据实际流量调整，否则预扣事务会在连接池获取处超时。

### 排查路径
1. **服务启动与数据库故障**：查看系统标准输出 `log/slog` 日志。关键字 `migration failed` 表示数据库表结构迁移异常，`database is locked` 表示 SQLite 并发冲突。
2. **请求超时与上游报错**：登录管理后台访问「请求日志」，过滤对应模型的非 200 请求，查看上游返回的具体错误码（如 `insufficient_quota` 或 `context_length_exceeded`）。
3. **运行时资源与协程泄漏**：登录管理后台「系统资源」或请求 `/api/health`，核对活动 Goroutine 数量与数据库闲置/活动连接数。
