# 服务健康与可用性监控

本文档说明 Obsidian Arc 的模型健康度计算、主动探测机制、断路器熔断与数据脱敏规则。

---

## 监控架构设计

### 真实流量与轻量主动探测双轨机制

#### 做了什么
系统采用双轨机制采集模型可用性数据：
1. **真实请求采样**：正常处理用户的实际调用时，记录请求成功/失败状态与往返耗时；
2. **主动轻量探测**：当某个模型在配置的时间窗口内（默认 15~30 分钟）未发生任何用户调用时，后台巡检协程会向上游发送包含单个 Token 的最小化探测请求。

```text
               ┌───────────────────────┐
               │    真实用户流量        │──► 记录成功 / 失败样本
               └───────────────────────┘
                           │
       模型是否在滑动窗口内活跃？
         ├── 是  ──► 跳过主动探测，直接使用用户样本判定
         └── 否  ──► 触发主动探针：发送 1 个 Token 的微型请求
```

#### 为什么这么做
高频主动向数十个模型发送长提示词会产生持续的 Token 费用开销；而仅探测静态 HTTP 端口无法验证上游模型服务内部是否正常。以真实流量为主、空闲时补充最小探针，可以在控制 API 费用的同时维持全量模型的可用性感知。

#### 代价是什么
1. **冷门模型存在检测滞后**：长期无用户调用的冷门模型仅能按照设定的探测间隔（如 15 分钟）更新一次状态，无法在发生故障的第一时间捕获；
2. **探针消耗基础额度**：在模型数量较多的实例中，即使发送最小化请求，全天累计的主动探针仍会消耗少量的上游调用额度与日志存储空间。

## 状态定义与阈值

系统根据滑动窗口内的采样数据计算模型状态：

| 状态徽标 | 状态标识 | 判定条件 | 说明 |
| :--- | :--- | :--- | :--- |
| 🟢 **正常** | `up` | 可用率 $\ge 99\%$ | 请求正常响应无异常。 |
| 🟡 **降级** | `degraded` | 可用率低于警报线（默认 $< 90\%$） | 部分请求出现超时、上游 5xx 或频控拦截。 |
| 🔴 **故障** | `down` | 触发断路熔断或连续探测失败 | 上游不可达或连续报错已自动从前台下线。 |
| ⚪ **未知** | `unknown` | 窗口内采样数少于判定下限 | 新添加或长期未被访问且未完成首轮探测的模型。 |

## 自动化断路器与自愈

### 做了什么
系统提供两种维度的自动熔断配置：
1. **连续失败熔断 (`health.disable_after`)**：当模型连续调用失败达到指定次数（如 3 次）时，断路器自动将该模型标记为 `AutoDisabled`，在前台模型选择器中对其进行隐藏；
2. **成功率熔断 (`health.disable_below`)**：滑动窗口内的成功率百分比跌破阈值（如 70%）时触发熔断。

熔断后，后台探针以设定的低频率继续探测上游。当探针连续返回成功达到恢复阈值后，系统自动清除禁用状态，恢复前台展示。

### 为什么这么做
当特定上游供应商发生区域性故障时，及时将故障模型从用户可见列表中移除，避免终端用户因反复选用故障模型而遭遇错误。故障恢复后自动重新上线，减少人工介入的运维成本。

### 代价是什么
断路器若判定过于激进（如将连续失败阈值设为 1 或 2），在公网出现瞬时抖动时容易造成模型频繁下线与上线，导致正在使用该模型对话的用户遇到模型突发不可见的问题。

## 24 柱时间线与指标重置

- **24 柱直方图**：健康面板按小时划分为 24 个时间片，每个时间片以颜色柱表示可用率分布（绿色 100%、黄色存在降级、红色故障），鼠标悬停可查看具体的样本数量与失败计数；
- **重置指标 (`Reset Uptime`)**：管理员更换上游 Key 或修复网络后，可手动触发重置。系统记录当前时间戳，此前的历史失败样本不再计入可用率分母，状态立即按新产生的调用重新计算。

## 普通用户可见看板与脱敏

管理员可通过 `health.show_users=true` 开放普通用户查看 `/uptime` 看板的权限：
- **脱敏范围**：普通用户端的数据流中，服务端主动剥除服务商名称（Provider Name）、真实 Base URL、自定义 HTTP 请求头等后端运维信息；
- **展示范围**：仅保留模型对外展示名称、可用率数值与 24 柱历史状态条。

## 运维约束与排查路径

### 失效场景
1. **上游返回假 200**：若上游服务商在模型崩溃时依然返回 HTTP 200，且在文本中包含“由于网络原因生成失败”等自然语言错误提示，系统会将其误记为成功请求；
2. **探针被上游频控封禁**：若服务商对空闲探测设有限流规则，探针本身可能触发 429 报错，导致原本正常的模型被错误判定为故障并触发熔断。

### 不明显的约束与前提
1. **真实请求优先于主动探测**：模型在采样窗口内有任何真实用户调用时，系统跳过主动探测协程，直接使用用户样本判定状态；
2. **熔断与恢复自动闭环**：触发熔断后模型在前台隐藏，但后台探针仍保持低频探测，一旦上游网络恢复并连续探测成功达到阈值，系统自动解除禁用并恢复前台展示；
3. **指标重置时效性**：手动点击重置可用性统计仅调整统计起算时间戳，不抹除数据库中存储的底层日志明细。

### 排查路径
1. **模型被误下线**：登录管理后台「服务健康」，核对该模型的连续失败计数与近期错误日志，确认是否因上游偶发超时触发了 `health.disable_after`；
2. **探针未按期执行**：检查进程标准输出日志中是否有 `probing model` 相关的 debug/info 日志，确认后台巡检协程是否在正常运行。
