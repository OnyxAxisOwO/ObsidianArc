# 配额、用量账本与兑换卡

本文档说明 Obsidian Arc 的配额继承层级、滑动时间窗口计算、两阶段原子锁扣减机制与用量审计账本。

---

## 配额继承层级架构

系统支持三层配额策略继承与覆盖：

```text
┌──────────────────────────────────────────────┐
│           全局策略 (Global Policy)            │  ◄── 实例默认兜底限制
└──────────────────────────────────────────────┘
                       │ 继承 / 覆盖
                       ▼
┌──────────────────────────────────────────────┐
│          用户组策略 (Group Policy)            │  ◄── 按角色或分组定制
└──────────────────────────────────────────────┘
                       │ 继承 / 覆盖
                       ▼
┌──────────────────────────────────────────────┐
│           用户策略 (User Policy)              │  ◄── 针对特定个人覆盖
└──────────────────────────────────────────────┘
```

### 解析规则
请求进入时，系统按照 **用户专属策略 -> 用户所属用户组策略 -> 实例全局策略** 的顺序逐级解析。若下级未定义某项约束，则自动继承上级配置；下级显式配置的数值将完全覆盖上级。

## 滑动时间窗口与约束维度

系统支持在以下四个独立的时间跨度上施加限额：
- **5 小时滚动窗口**：用于削减高频突发调用峰值；
- **自然日窗口**：每日累计上限；
- **自然周窗口**：每周累计上限；
- **自然月窗口**：每月累计上限。

每个时间窗口内可独立设置三项约束指标：
1. **请求总次数 (Requests)**；
2. **总消耗 Token 数量 (Tokens)**（包含输入、输出与推理思考 Token）；
3. **计费点数 (Credits)**（根据模型配置的价格倍率核算出的消耗点数）。

## 并发防超售：两阶段行级锁

### 做了什么
配额核算分为预检预扣与最终结算两个独立阶段，均在数据库事务中通过显式锁定用户记录行完成：

```text
[1. 预检预扣阶段]
开启短事务 ──► UPDATE users SET updated_at = ... WHERE id = ? 锁定用户行
按模型配置的最大输出 Token 预扣额度
      ├── 额度不足 ──► 立即返回 429 Too Many Requests
      └── 额度充足 ──► 提交事务，释放数据库连接，向上游发起流式请求
            │
[2. 流式生成阶段]
仅持有网络 Socket 进行文本传输，不持有数据库连接
            │
[3. 结算归还阶段]
生成结束（或中途断开） ──► 使用 context.WithoutCancel 开启新事务
锁定用户行 ──► 归还预扣额度 ──► 扣除真实产生的 Token/点数 ──► 提交事务
```

### 为什么这么做
如果不使用行级锁，在高并发场景下同一用户的多个请求并发执行“先查额度再扣费”时，所有请求均会读取到旧的额度余额，导致实际消耗远超设定配额（即并发超售）。
将预扣与结算解耦为两个极短事务，可以避免在模型流式输出过程中长时间占用数据库连接。

### 代价是什么
1. **相同账户并发请求排队**：同一用户的并发请求必须在数据库事务中按序排队获取行锁，高并发时会增加排队等待耗时；
2. **预扣占用额度**：在流式生成期间，账户的可用额度扣除了“最坏情况预估值”，可能导致用户在并发发起多个请求时，即便总余额充足也被临时拦截；
3. **未正常结算的挂起记录**：若服务进程在流式传输中突发断电退出，预扣的额度未能进入结算阶段，需依赖系统周期性巡检任务（10 分钟一次）识别并释放超时的未结算预扣。

## 用量审计账本 (`usage_records`)

每一次成功的生成、中断或服务端报错均会生成一条审计流水并写入 `usage_records` 表：
- **基础元数据**：用户 ID、用户组 ID、服务商 ID、模型 ID、会话 ID、全局请求 ID；
- **用量明细**：输入 Token、输出 Token、推理 Token、计算点数（Credits）；
- **执行指标**：请求起止毫秒时间戳、首字延迟（TTFT）、最终状态码与状态标记（`completed` / `cancelled` / `failed`）。

用户可在个人中心「用量账本」查看自己的消耗明细；管理员可在管理后台查看全站用量趋势并导出 CSV 报表。

---

## 额度展示模式 (`quota.usage_display`)

管理员可在系统设置中选择前台额度展示形式：
- `remaining`：展示剩余百分比（例如“剩余 80%”）；
- `used`：展示已用百分比（例如“已用 20%”）；
- `absolute`：展示具体数值（例如“已用 100,000 / 500,000 Tokens”）。

---

## 兑换卡码机制

系统提供批量生成与核销兑换卡码功能：
- **额度重置卡**：兑换后重置用户当前滑动窗口的用量计数；
- **防暴力破解**：兑换接口按客户端 IP 记录错误尝试次数，触发连续错误时进行指数退避限制；
- **作废与撤销**：管理员可随时手动吊销未核销的卡码使其失效。

## 运维约束与排查路径

### 失效场景
1. **上游不返回 Token 计费字段**：若上游服务商在流式结束时不返回 `usage` 对象（部分非标准中转可能缺少此字段），系统必须依赖本地分词器估算 Token 数，可能与实际账单产生微小偏差；
2. **时钟不同步**：若多节点部署时服务器系统时间未对齐（NTP 漂移），会导致滑动时间窗口计算出现边界偏差；
3. **SQLite 高频写锁超时**：多用户同时大量高频兑换卡码或并发扣费时，SQLite 写入可能因等待行级锁超时抛出 `database is locked`。

### 不明显的约束与前提
1. **两阶段原子锁排他性**：预扣和结算必须在短事务中显式更新 `users` 表的 `updated_at` 获取数据库行锁，并发请求在数据库连接层排队，若连接池满则抛出等待超时；
2. **最坏情况预扣占用**：预扣阶段直接按模型的最大输出 Token 扣除额度，即使最终回答仅消耗极少 Token，在推流未结束前这部分额度均处于锁定状态；
3. **未结算挂起清理机制**：因断电或异常终止导致未能进入结算阶段的预扣记录，依赖每 10 分钟执行一次的后台巡检协程识别并释放，无法实时立即解冻。

### 排查路径
1. **用户反映额度被异常冻结**：在数据库中查询 `usage_records` 表中状态为 `pending` 且创建时间超过 10 分钟的记录，确认定时巡检任务是否正常清理释放；
2. **扣费异常排查**：在管理后台根据用户 ID 过滤「用量统计」流水，核对每次请求记录的输入/输出 Token 与对应的点数折算倍率。
