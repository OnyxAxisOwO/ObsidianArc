# 多用户与权限分组

本文档说明 Obsidian Arc 的用户账户模型、用户组权限架构、模型授权机制与偏好设置漫游。

---

## 账户模型与生命周期

### 1. 会话与登录态
- 用户登录凭证存放于带有 `HttpOnly; SameSite=Lax` 属性的 Session Cookie 中；
- 采用内存读缓存与落盘间隔（默认 1 小时）控制会话活跃时间刷新频率，降低高频请求对数据库的写 I/O 压力。

### 2. 账号管理
- **封禁/解封**：封禁操作会注销该用户所有活跃 Session，并在网关层拦截后续的 API 与 Web 请求；
- **重置密码**：管理员可在后台为遗忘凭证的用户重置密码；
- **角色分配**：支持普通用户 (`user`) 与超级管理员 (`admin`) 角色切换。

---

## 用户组体系 (User Groups)

用户组是管理模型授权与配额限制的核心载体。管理员可创建自定义分组（如研发组、业务组、访客体验组等）。

```text
┌─────────────────────────────────────────────────────────────┐
│                       用户组 (User Group)                    │
├──────────────────────────────┬──────────────────────────────┤
│        模型授权白名单         │          配额限制策略         │
├──────────────────────────────┼──────────────────────────────┤
│  • gpt-4o                    │  • 5 小时限额: 200,000 Tokens│
│  • claude-3-7-sonnet         │  • 每日限额: 1,000,000 Tokens │
│  • deepseek-chat             │  • 共享点数与频控限制         │
└──────────────────────────────┴──────────────────────────────┘
               ▲
               │ 关联
     ┌─────────┴─────────┐
     ▼                   ▼
 用户 Alice            用户 Bob
```

### 默认注册用户组 (`registration.default_group`)
系统必须指定一个默认用户组（初始化时自动生成 `Default` 组）。新用户注册成功后自动归入该组，继承该组绑定的模型和配额。默认组不能被直接删除，若需删除必须先将其他组设为默认组。

---

## 组级四大门禁开关

在编辑用户组时，系统提供 4 项独立的权限门禁开关：

| 权限开关 | 对应字段 | 说明 |
| :--- | :--- | :--- |
| **全模型自动授权** | `allow_all_models` | 开启后，该组成员自动具备全站所有已启用模型的调用权限。新增模型无需逐组重新分配。 |
| **API 接口调用门禁** | `api_access` | 控制该组成员是否有权创建 API Key 以及通过 `/v1` 调用网关接口。关闭后仅允许使用网页端对话。 |
| **耗时统计行可见性** | `allow_stats` | 控制成员在收到回答后，是否在底部展示耗时、首字延迟与 Token 速率信息。 |
| **会话删除合规防删** | `allow_delete_conversations` | 开启后允许用户自行删除历史会话；关闭后前端隐藏删除按钮，服务端拦截删除接口，用于满足会话留痕审计需求。 |

## 模型授权机制

### 做了什么
若用户组未开启 `allow_all_models`，系统根据模型配置的授权关系进行严格权限校验：
- 未授权的模型在前台模型切换下拉菜单中被过滤，不向用户展示；
- 携带 API Key 调用未授权模型时，网关在请求进入阶段返回 `404 Not Found`（错误码 `model_not_found`）。

### 为什么这么做
支持按团队或预算分配不同等级的模型资源（例如将高单价思考模型限定为特定开发组使用，普通组仅能使用轻量模型）。

### 代价是什么
管理员新增模型时，若未开启全模型自动授权，必须进入每个相关用户组手动勾选该模型，增加了多组维护的操作步骤。

---

## 至少保留一名管理员约束

### 做了什么
在降级管理员、封禁管理员或删除管理员账号时，系统在数据库事务中通过行锁锁定用户表并统计当前活跃管理员数量。若操作会导致全站无有效管理员，事务直接中止并返回错误。

### 为什么这么做
防止因误操作或并发请求导致系统中所有管理员账号均被删除或降级，造成系统脱管。

### 代价是什么
单管理员环境下若需要交接权限，必须先创建或晋升新的管理员，才能对原管理员执行降级或删除操作。

---

## 偏好设置云端漫游

用户在界面调整的配置（默认模型、思考预算等级、主题颜色、背景壁纸与透明度）统一持久化于 `user_preferences` 表中：
- 登录后由前端拉取并在本地应用；
- 切换不同浏览器或设备时自动保持一致。

---

## 运维约束与排查路径

### 失效场景
1. **用户无法获取指定模型**：若用户反映下拉列表中缺少某个模型，检查该模型是否未被勾选分配给用户所在的用户组，或者该模型是否因触发熔断而被系统自动下线；
2. **API 调用返回 403 api_disabled**：检查用户所在用户组的 `api_access` 开关是否处于关闭状态；
3. **删除用户组失败**：若该用户组被标记为默认组，或者组内仍有存量用户，系统拦截删除操作，需先迁移成员并调整默认组。

### 不明显的约束与前提
1. **默认用户组存在性保证**：系统生命周期内必须有且仅有一个默认组，新注册用户自动归入默认组，默认组不可被删除；
2. **原子防降级锁**：修改管理员角色时，数据库事务持有行锁统计活跃管理员总数，若剩余管理员为 1，任何降级或封禁该管理员的操作均被拦截；
3. **模型权限动态计算**：普通用户获取模型列表时，服务端动态计算用户组白名单并结合模型启用状态，用户组未勾选的模型在前台完全不可见。

### 排查路径
1. **用户权限核对**：在管理后台「用户管理」中搜索目标用户，查看其所属用户组，再进入「用户组管理」核对该组的模型白名单与门禁开关；
2. **审计日志追踪**：在管理后台「请求日志」中按用户名筛选，查看其历史调用返回的具体错误码。
